## שלב 0 — אבחון read-only (בוצע, ללא נגיעה בקוד)

### א. מבנה ה-trade ומה נדרש כדי שעסקה תיחשב "סגורה"

מקור: `src/import/normalizeRow.js:120-155`, `src/intelligence/utils/statisticalModels.js:37`,
`src/utils.js:29-42`, `src/supabaseClient.js:29-55`.

| שדה | ערך היום ביבוא | מה FIFO צריך לשנות |
|-----|-----------------|---------------------|
| `status` | `exit != null ? "CLOSED" : "OPEN"` | חייב `"CLOSED"` בעסקה משודכת |
| `exit` | `num(cell("exit"))` — **null בקבצי ברוקר** (אין עמודת exit) | מחיר המכירה המשודכת |
| `closedAt` | `${exitDate \|\| date}T20:00:00` ISO | תאריך שורת המכירה |
| `date` / `createdAt` | תאריך השורה, `T14:30:00` | תאריך שורת **הקנייה** |
| `entry` | מחיר השורה | מחיר הקנייה |
| `shares` | `Math.abs(qty)` כשיש sideResolver | הכמות **המשודכת** |
| `stop` / `target` | `null` בקבצי ברוקר | נשאר `null` |

**הגדרת "סגורה" נעולה (T3):**
```js
// src/intelligence/utils/statisticalModels.js:37
export const getClosed = (trades) => (trades || []).filter(t => t && t.status === "CLOSED" && t.exit != null);
```
שני התנאים גם יחד. `status:"CLOSED"` בלי `exit` = עסקה שנעלמת מכל סטטיסטיקה בשקט.

**P&L — לא נשמר.** `calcTradeMetrics` (`src/utils.js:29`) גוזר `pnl` ו-`rMultiple`
בכל קריאה, ואין עמודת `pnl` ב-`TRADE_COLUMNS`. אחסון מחושב-מראש יפר מקור-אמת-אחד.
→ **המנוע לא כותב `pnl`.**

**חוזה ה-R נשמר:** `stop == null` → `rMultiple: null` (לא 0). עסקאות FIFO ייכנסו
בלי סטופ, ולכן ייצאו נכון מכל מדד מבוסס-R במקום להיגרר ל-0.

### ב. שדות זמן בשורות ברוקר — **תאריך בלבד, אין שעה**

מקור: `src/import/brokerProfiles.js:25-53`.

| ברוקר | עמודות תאריך | שעה |
|-------|---------------|-----|
| IBI | `תאריך הוראה`, `תאריך נכונות` (DD/MM/YYYY) | **אין** |
| אלטשולר שחם | `תאריך` | **אין** |

**השלכה:** אין סדר תוך-יומי. מיון לפי תאריך בלבד, ושובר-שוויון = **סדר השורות
בקובץ** (כלל 1). **כמה מקרים זה באמת נוגע בהם — לא נמדד.** בשלב 4 נספור, על
שני הקבצים האמיתיים, כמה זוגות קנייה-מכירה של אותו נייר נופלים באותו יום מתוך
כמה זוגות בסך הכול, ונדווח מונה/מכנה (§2). עד אז זו הנחה, לא נתון —
ראה §סיכונים ב'.

### ג. עמלות (כלל 6)

אלטשולר מייצא `עמלת פעולה` ו-`עמלות נלוות`; IBI מייצא `אחוז מס` ו-
`סכום מס משוער בישראל`. **אין ב-`TRADE_COLUMNS` שום עמודת עמלה או מס.**
→ לפי הוראתך המפורשת: **מתעלמים ומדווחים, לא ממציאים שדה.**
המנוע יספור כמה שורות נשאו עמלה >0 ויחזיר את הסכום ב-`log` בלבד, כדי שהמידע
לא ייעלם בשקט (§2). לא מוצג ולא נשמר בשלב הזה.

## סעיף ציד — 3 ממצאים

### 1. 🔴 `dupKey` הופך כל פיצול לכפילות שקרית — **חוסם**

```js
// src/import/buildImport.js:8
const dupKey = (t) => `${String(t.ticker).toUpperCase()}|${t.date}|${Number(t.entry)}`;
```
המפתח הוא **ticker|date|entry** — בלי `exit`, בלי `shares`, בלי `closedAt`.

תרחיש פיצול תקני: קנייה 100 @150 ב-01/03, מכירה 40 @160 ב-05/03, מכירה 60 @170
ב-08/03. FIFO מייצר שתי עסקאות סגורות, שתיהן `ACME|2026-03-01|150` — **מפתח זהה**.
`seenInFile` תופס את השנייה ככפילות.

ו-`importDupes` ברירת מחדל `false` (`ImportJournalModal.jsx:28`) → **העסקה השנייה
פשוט לא נכנסת.** כלומר מנוע FIFO ללא תיקון כאן *מוחק* חלק מהמכירות בשקט —
בדיוק סוג הכשל השקט ש-§2 אוסר.

**התיקון המוצע:** הרחבת `dupKey` ל-`ticker|date|entry|exit|shares|closedAt`.
- שתי עסקאות פיצול נבדלות ב-`exit`+`shares`+`closedAt` → אין התנגשות.
- יבוא כפול של אותו קובץ → כל השדות זהים → עדיין נתפס ככפילות. ✅
- המסלול הגנרי: קובץ עם entry+exit בשורה אחת — היום שתי שורות שנבדלות רק ב-exit
  נחשבות כפילות; אחרי התיקון לא. זו **הרחבה של דיוק, לא רגרסיה** — אבל היא
  משנה התנהגות קיימת, ולכן דורשת אישור מפורש ובדיקה ייעודית.

**תשובה לשאלתך:** לא, תרחיש הכפילויות הקיים (בדיקה 6) **אינו** מכסה עסקאות
מורכבות-FIFO. הוא בודק ticker+date+entry זהים בלבד.

### 2. ✅ עסקה סגורה מיובאת נכנסת לסטטיסטיקה בדיוק כמו ידנית

`getClosed` בודק `status` ו-`exit` בלבד — אין בו שום אבחנה בין מקורות.
עסקת FIFO עם `status:"CLOSED"` + `exit` מספרי נכנסת לכל חישוב זהה לחלוטין.
`calcTradeMetrics` גוזר `pnl = (exit-entry)*shares` (הפוך ב-SHORT) — אותו קוד.
ההבדל היחיד: `stop:null` → `rMultiple:null`, וזה **התנהגות נכונה** לפי חוזה ה-R.

### 3. ⚠️ אין דגל מקור — עסקה מיובאת בלתי-ניתנת לזיהוי

`TRADE_COLUMNS` מכיל `is_demo` בלבד. `normalizeRow` קובע `isDemo: false`.
אין `source`, אין `imported_at`, אין `import_batch_id`.
**השלכה:** אם FIFO ישדך שגוי, אין דרך לבודד את העסקאות שהוא יצר ולהתאושש —
לא בשאילתה ולא בממשק. זה חוב אמיתי, אבל הוספת עמודה = מיגרציה (§12: ניב מריץ
ידנית). **לא בהיקף T5.** → שורה ב-`docs/STATE.md` ⚠️ באותו קומיט (§10.1).

## כללי המנוע — נעולים מראש (מהפרומפט, ללא שינוי)

1. FIFO קלאסי per-ticker. מכירה סוגרת את הקנייה הפתוחה **הוותיקה ביותר** של אותו
   נייר. מיון לפי תאריך; שובר-שוויון = סדר שורות בקובץ.
2. שידוך חלקי: קנייה 100 + מכירה 40 → סגורה 40 + פתוחה 60. מכירה 100 מול קניות
   40+60 → **שתי** עסקאות סגורות (המכירה מתפצלת).
3. מכירה בלי קנייה קודמת = SHORT פתוח, **לא שגיאה** — המסלול הקיים.
4. מה שנשאר לא-משודך = עסקאות פתוחות, נכנסות כרגיל.
5. שדות העסקה הסגורה: entry=מחיר קנייה, exit=מחיר מכירה, shares=כמות משודכת,
   תאריכים בהתאם, status CLOSED. **P&L לא נשמר** (מאושר בשלב 0א).
6. עמלות: אין עמודה → מתעלמים ומדווחים ב-`log` (מאושר בשלב 0ג).

## היקף ועיצוב

### `src/import/fifoMatch.js` — פונקציה טהורה

```js
// trades: Trade[]  (פלט normalizeRow, בסדר השורות המקורי)
// → { closedTrades: Trade[], openTrades: Trade[], log: {...} }
export function fifoMatch(trades) { ... }
```

- **אפס תלות ב-UI**, אפס import מ-React, בדיקה בבידוד מלא.
- רץ **אחרי** `normalizeRow`, **לפני** התצוגה.
- מיון יציב: `date` עולה, שובר-שוויון `_rowIndex` (נוסף פנימית, לא נשמר).
- מבנה עבודה: `Map<ticker, Queue<{trade, remaining}>>`.
- כל עסקה סגורה מקבלת `id` חדש (`crypto.randomUUID`), `date`/`createdAt` מהקנייה,
  `exit`/`closedAt` מהמכירה, `shares` = הכמות המשודכת.
- `log`: `{ matched, partialFills, splitSells, orphanSells, unmatchedBuys, feesSeen }`.

### ⚠️ שער ההפעלה

FIFO פעיל **רק כשזוהה פרופיל ברוקר** (`applied != null` ב-`ImportJournalModal`).
המסלול הגנרי — קבצים שכבר נושאים entry+exit בשורה אחת — **לא נוגעים בו**.
בדיקה 0 (baseline) והתרחישים 1-17 חייבים לעבור כמות שהם.

### תצוגה

תוספת לשורת המונה של T4, **לא החלפה**:
`"X עסקאות סגורות (שודכו) · Y פתוחות"` — מפתח i18n חדש `imp_fifo_summary`
(EN+HE). מוצג רק כשהמנוע רץ.
