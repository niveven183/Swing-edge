### ב. איך נבחרת שורת הכותרת היום

`parseFile.js:19` — **השורה הראשונה שאינה ריקה**, תמיד. אין פרמטר, אין עקיפה.
ההנחה בפרומפט ("שורה 0 תמיד") נכונה מעשית, אבל **הבעיה חמורה מהמנוסח**, בגלל
`parseFile.js:20`:

```js
const headers = rowsRaw[0].map(...);
const width = headers.length;      // ← הרוחב נגזר משורת הלוגו
```

`width` מקבע את מספר העמודות של **כל** השורות. שורת לוגו של ברוקר אמיתי אינה
מכילה פסיקים, ולכן היא באורך תא אחד — וכל הטבלה נחתכת לעמודה אחת. פלט מדיד:

```
headers = ["דוח תנועות בחשבון"] width = 1
rows    = [["בית השקעות IBI"],["שם נייר"],["AAPL"]]
```

**שש עמודות מתוך שש הושמדו בשלב הפרסינג.** לכן תיקון שמזהה את שורת הכותרת
*אחרי* `matrixToTable` אינו יכול לעבוד — אין לו על מה לעבוד. **הפרופיל חייב
לרוץ על המטריצה הגולמית.** זו האילוצה הארכיטקטונית המרכזית של השלב הזה.

כשהלוגו כן נושא פסיקים (רוחב נשמר), התוצאה היא ההרס ה"רך":

```
headers = ["דוח תנועות בחשבון","","","","",""]
mapping = {"date":5}
counts  = {"total":9,"valid":0,"rejected":9}   ← 9/9 = 100% נדחו, כולן no_ticker
```

### ג. מה קורה לשורת "דיבידנד"/"המרת מט"ח" היום

**התשובה היא "שניהם, ובכיוון ההפוך מהרצוי."** הרצתי את הצינור על קובץ שכותרותיו
*כן* זוהו נכון (כלומר: אחרי שנתקן את ב', זה מה שייוותר):

```
counts = {"total":6,"valid":3,"rejected":3}
   VALID  AAPL side=LONG shares=10   entry=150     ← קניה, נכון
   VALID  USD  side=LONG shares=1000 entry=3.7     ← המרת מט"ח!
   VALID  BAC  side=LONG shares=1    entry=12.5    ← חיוב ריבית!
   REJECT row2 no_qty  ["TSLA","1159251","מכירה","-5",...]   ← מכירה אמיתית
   REJECT row3 no_qty  ["AAPL","1159250","דיבידנד","0",...]
   REJECT row5 no_entry ["NVDA","1159252","מתנה","3","0",...]
```

**2 מתוך 3 השורות שנקלטו כעסקאות אינן עסקאות.** המרת מט"ח נכנסת כ"קניית 1000
מניות USD ב-3.7", וחיוב ריבית כ"קניית מניה אחת של BAC ב-12.5". שתיהן `LONG`,
שתיהן ייכנסו ליומן, שתיהן ייספרו בכל סטטיסטיקה. במקביל, **המכירה האמיתית
נדחית** — כי `-5` נופל על `shares <= 0` (`normalizeRow:92`).

זהו כשל שקט מסוג §2 בצורתו הגרועה: לא "נכשל בשקט" אלא **"הצליח בשקט עם נתון
שקרי"**. הוא לא נספר באף מונה שגיאות, והמשתמש רואה "3 עסקאות תקינות" ירוק.
הדחייה (`no_qty` על מכירה) לפחות נראית; הקליטה השקרית לא.

### ד. `side` היום

`normalizeSide` (`synonyms.js:87`) מקבל טקסט בלבד. פלט מדוד:

| קלט | פלט | | קלט | פלט |
|---|---|---|---|---|
| `"קניה"` / `"קנייה"` | `LONG` | | `"דיבידנד"` | `null` |
| `"מכירה"` | `SHORT` | | `"המרת מט\"ח"` | `null` |
| `"Buy"` / `"Sell"` | `LONG` / `SHORT` | | `"מתנה"` | `null` |
| **`"מכר"`** | **`null`** ⚠️ | | `"-5"` | `null` |

`"מכר"` (צורה נפוצה בדוחות) אינו נתפס: הענף בודק `k.includes("מכיר")`.

**כמות שלילית — שלוש הצורות נדחות:**

```
qty=-19  -> REJECT no_qty
qty=19-  -> REJECT no_qty     ← הצורה שבפרומפט
qty=(19) -> REJECT no_qty     ← num() מחזיר -19, ואז shares<=0
```

`num()` דווקא מפרש `(19)` כ-`-19` נכון, אבל `19-` (סיפרה ואז מקף) מתפרק:
`s.replace(/[^\d.\-]/g,"")` משאיר `"19-"`, ו-`Number("19-")` הוא `NaN` → `null`.
**שלוש צורות, שלוש דחיות, אף אחת לא הופכת ל-SHORT.**

#### ד2. הטאוטולוגיה של F4 — האימות המדויק

`normalizeRow:94-101`:

```js
let side = normalizeSide(cell("side"));
if (!side) side = inferSide(entry, stop, target);        // :95
if (stop != null && stop > 0) {
  const v = validateTradeInputs(entry, stop, target, side);   // :99
```

מדדתי את שני הענפים בנפרד — **הטאוטולוגיה חלקית, לא מלאה**, וזה משנה את הניסוח:

| מצב | `inferSide` בוחר לפי | האם `validateTradeInputs` יכול להיכשל? |
|---|---|---|
| `stop` בלבד, בלי `target` | הסטופ | **לא לעולם** — טאוטולוגיה מלאה |
| `target` קיים | היעד | כן — הסטופ נבדק מול ציר עצמאי |
| **אין `stop` כלל (קובץ ברוקר)** | — | **הבדיקה מדולגת כליל** (`:98`) |

השורה השלישית היא המקרה של כל קובץ ברוקר: אין סטופ, ולכן `inferSide(entry, 0, 0)`
נופל ל-`return "LONG"` (`utils.js:58`) ואף אחד לא בודק דבר. פלט מדוד:

```
D2) no side column, no stop/target:  -> side=LONG
```

**כל שורה בקובץ ברוקר בלי עמודת side מקבלת `LONG` בשתיקה.**

**בפרופילים זה מתהפך:** `side` יגיע ממקור עצמאי — סימן הכמות (IBI) או טקסט
"סוג פעולה" (אלטשולר) — ולא מהגיאומטריה. מרגע זה `validateTradeInputs` חוזר
להיות בדיקה אמיתית, כי הוא משווה `side` חיצוני מול גיאומטריה, ולא את הגיאומטריה
מול עצמה. **זו הסיבה שהפרופיל הוא גם תיקון נכונוּת ולא רק תיקון קליטה.**

## התכן

### קובץ חדש — `src/import/brokerProfiles.js`

```js
// profile = {
//   id,                          // "ibi" | "altshuler"
//   detect(matrix)  -> boolean,  // טביעת אצבע, לא ניחוש

//   sideFrom(row, ctx)  -> "LONG" | "SHORT" | null,

export function detectProfile(matrix) -> profile | null
export function applyProfile(profile, matrix) -> { headers, rows, skipped[] }
```

### שינוי מינימלי ב-`parseFile.js` — חשיפת המטריצה הגולמית

מסקנת §0.ב: הפרופיל חייב לראות את המטריצה לפני הריבוע. שתי תוספות **אדיטיביות
בלבד**:

1. `matrixToTable(matrix, headerIdx = null)` — `null` = ההתנהגות הקיימת, מילה במילה.
2. הערך המוחזר מ-`parseCSV`/`parseXLSX` מקבל שדה נוסף `matrix`.

אין שינוי בחתימה, אין שינוי בהתנהגות למי שלא מעביר `headerIdx`. **המסלול הגנרי
מחזיר בייט-אחד-לאחד את מה שהוא מחזיר היום** — וזה בדיוק מה ששער ה-baseline מוכיח.

### זיהוי שורת הכותרת — דינמי

`headerRow(matrix)` = **השורה הראשונה שבה ≥4 תאים מחזירים `matchHeader` לא-null,
ולפחות 3 שדות קנוניים שונים**. לא אינדקס 11, לא "השורה הראשונה עם 6 פסיקים".
הסף הכפול (מספר תאים + מגוון שדות) מונע שורת סיכום כמו "סה"כ / כמות / שער"
מלהיתפס ככותרת.

### `rowFilter` — whitelist, לא blacklist

שמונת סוגי הפעולה שנצפו: קניה · מכירה · דיבידנד · המרת מט"ח · מתנה · מבצע ·
חיוב ריבית · ציטוט זמן אמת. **שניים הם עסקאות.**

הפרופיל **ישמור רק** קניה/קנייה/מכירה/מכר, ולא "יסנן את השישה". הנימוק ישיר
מ-§0.ג: הכשל הוא קליטה שקרית, לא דחייה. blacklist נכשל *פתוח* — סוג פעולה
חדש שהברוקר יוסיף מחר ייכנס כעסקה. whitelist נכשל *סגור*.

**וכדי שהסגירה לא תהיה שקטה** (§2): כל שורה שסוננה נספרת ב-`skipped` **עם סוג
הפעולה שלה**, ומוצגת במסך הסקירה כשורה נפרדת — לא "נדחו", אלא "שורות שאינן
עסקאות: 4 (דיבידנד 2 · המרת מט"ח 1 · חיוב ריבית 1)". המשתמש רואה בדיוק מה לא
נכנס ולמה.

### `sideFrom` + חוזה הכמות

| פרופיל | מקור ה-`side` |
|---|---|
| IBI | **סימן הכמות** — `19-` / `-19` / `(19)` → `SHORT`, חיובי → `LONG` |
| אלטשולר | **טקסט** "סוג פעולה" דרך `normalizeSide` |

**אינווריאנטה נלווית, מפורשת:** כשהסימן נצרך ככיוון, הוא **אינו** נקרא שוב
ככמות — `shares = Math.abs(shares)`. אחרת המכירה תמשיך ליפול על `shares <= 0`.
תיקון נלווה: `num()` יטפל בצורת הסיפא `19-` (היום `NaN`).

### החיבור ל-`normalizeRow` — בלי לגעת במסלול הגנרי

`normalizeRow` יקבל `opts.sideResolver` אופציונלי (`row -> side | null`):

* **`opts.sideResolver` חסר** → הקוד רץ בדיוק כפי שהוא רץ היום. אפס דלתא.
* **קיים ומחזיר `side`** → אותו `side` גובר על `inferSide`, והכמות נלקחת ב-`abs`.

זו התוספת היחידה ל-`normalizeRow`. `inferSide` נשאר fallback למסלול הגנרי.

## ❓ פתוח — דורש הכרעת ניב לפני ביצוע

**1. טביעת האצבע לזיהוי — אין לי את הקבצים האמיתיים.**
`detect()` אמור לזהות לפי מחרוזות כותרת ייחודיות, ואני לא ראיתי אף אחד משני
הקבצים. `ibi-style.csv` ו-`altshuler-style.csv` שבריפו הם סינתטיים משלב א' —
לגזור מהם טביעת אצבע ולקרוא לזה "זיהוי" יהיה בדיוק הניחוש שהפרומפט אוסר.
**נדרש:** שורת הכותרת המדויקת של כל קובץ + שורות הפתיח שמעליה ב-IBI (טקסט
מבני בלבד — בלי מספרי חשבון, שמות או יתרות). בלי זה אבנה `detect()` על סמך
המילון הקיים ואסמן אותו מפורשות כלא-מאומת.

**2. סף `headerRow` — 4 תאים / 3 שדות** הוא הצעה. אם שורת הכותרת של IBI צרה
מזה, הסף יזוז — עוד סיבה ל-(1).

**3. `"מכר"` → `SHORT`** ב-`normalizeSide` — תיקון של שתי מילים, אבל §13 מסמן
את מחרוזות ה-side כ-load-bearing (`VALID_EMOTIONS`, `DecisionCoach`). זו **הוספה**
בלבד ולא שינוי `value` קיים, ולכן לדעתי בטוחה — אך היא מחוץ להיקף שהוגדר.
מבקש אישור מפורש, או שאשאיר אותה לפריט נפרד.

**1. עוד הנחות "שורה 0"/"עמודה קבועה"?**
מלבד `parseFile.js:19-21` — **לא.** `detectColumns` מונע-אינדקס לחלוטין,
`normalizeRow` ניגש רק דרך `mapping`. הריכוזיות הזו היא מזל טוב: נקודת כשל
אחת, ולכן נקודת תיקון אחת. שים לב שהנגזרת של אותה שורה — `width` — היא
ההרסנית מבין השתיים (§0.ב).

**2. מה המשתמש רואה כשקובץ נכשל — הודעה מנחה או כלום?**
**כלום שימושי, ובשלושה מצבים שונים:**

| מצב | מה נראה | הבעיה |
|---|---|---|
| חריגת פרסר | `imp_parse_error`: "לא ניתן לקרוא את הקובץ…" | `ImportJournalModal.jsx:84` תופס `(e)` ו**זורק אותו**. השגיאה האמיתית לא נרשמת ולא נשלחת ל-Sentry |
| IBI (המצב בפועל) | הקובץ **נפתח בהצלחה**, ואז חסימה בשלב 2: "חסר שדה חובה: סימול, מחיר כניסה, כמות" | הכפתור מושבת. המשתמש רואה טבלה של תאים ריקים ומסר שמתאר תסמין, לא סיבה. **אין שום רמז לכך שהכותרות בשורה 11** |
| שורות שנקלטו שקרית | ירוק, "3 עסקאות תקינות" | §0.ג — אין מסר כלל |

ההודעה עצמה בסדר; **מה שחסר הוא שהשגיאה האמיתית לא שורדת בשום מקום.**
לא תיקנתי: זה מחוץ להיקף שהוגדר, ו-§11 דורש "וגם קשור למשימה וגם קטן ובטוח".

**3. דאטה חי — כמה משתמשים ניסו לייבא מאז 27.07?**
**לא ניתן לענות, ולא בגלל הרשאות — בגלל שהנתון לא קיים.**

* מקומית יש `VITE_SUPABASE_ANON_KEY` בלבד. `user-analytics.mjs` דורש
  `SUPABASE_DB_URL` שהוא סוד CI. §12: סודות = ניב בלבד. לא ניסיתי לגשת.
* **וגם אם הייתה לי גישה, השאילתה לא הייתה מחזירה את מה שנשאל.** האות היחיד
  ב-`user-analytics.mjs:158-196` הוא היוריסטיקת "שאריות ייבוא" — היא מזהה
  **עסקאות שנוצרו** ונראות מיובאות (`sig_predates` / `sig_1130` / `sig_batch`).
  ייבוא **שנכשל אינו יוצר אף עסקה**, ולכן אינו מותיר עקבה.
* `trackEvent` (`src/lib/consent.js:110`) אינו נקרא מ-`ImportJournalModal`
  ולמעשה **אינו נקרא מאף מקום באפליקציה** — 0 קוראים בכל `src/`.

**המסקנה, במונחי מונה ומכנה:** המכנה הזמין הוא "עסקאות שנוצרו ונראות מיובאות".
ייבוא כושל אינו יכול להופיע במכנה הזה. לכן כל מספר שאדווח היה מודד ייבוא
**מוצלח**, ומציג 0 כושלים — לא כי אין, אלא כי המכנה לא מסוגל להכיל אותם.
