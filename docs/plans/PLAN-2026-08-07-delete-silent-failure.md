## §1 — אבחון: איזו משלוש

**הכרעה: אף אחת משלושת המועמדות.** השורש הוא **מרוץ בין ה-INSERT ל-DELETE**,
ש-PostgREST הופך לבלתי-נראה. שלוש המועמדות נשללו בראיה, לא בהערכה.

### שלילת RLS — הראיה המכריעה

`restCleanup()` ב-`tests-sentinel/sentinel-auth.spec.js:225-286` מנפיק טוקן
למשתמש ה-QA (`auth/v1/token?grant_type=password`, שורות 238-244) ואז יורה
`DELETE /rest/v1/trades?ticker=eq.SNTNL` עם **אותו anon key** ו-**טוקן של אותו
משתמש** (שורות 257-265). כלומר: אותו משתמש, אותו מפתח, **אותה מדיניות**
`users own trades` (`20260708150000_trades_rls_policy.sql`, `for all` /
`using (auth.uid() = user_id)`).

הניקוי הזה **הצליח ומחק `n > 0` שורות** — זה בדיוק התנאי שהצית את הממצא
(שורה 270: `if (n > 0 && uiDeleteOk)`).

> אילו RLS חסם את המשתמש ממחיקת שורותיו שלו, הניקוי היה מוחק **0**, והממצא
> `ui-delete-incomplete` לא היה יכול להיווצר מלכתחילה. **הממצא עצמו הוא
> ההוכחה ש-RLS תקין.**

חיזוק שני: RLS הוא דטרמיניסטי. תקלת מדיניות הייתה מפילה **12/12** ריצות
ב-6 שעות, לא 3.

### שלילת שגיאת רשת

כשל תעבורה **דוחה** את ה-promise. `handleDeleteTrade` עוטף ב-`try/catch`
(`SwingEdge_App.jsx:2477-2483`), ולכן היה מגיע ל-
`console.error("Supabase delete threw:", e)`. הכשל לא היה שקט לחלוטין, ובעיקר —
לא היה **מתואם לתזמון יצירה→מחיקה** כפי שהוא בפועל.

### שלילת race עם hydration

אפקט הטעינה (`SwingEdge_App.jsx:1495-1526`) תלוי ב-`[authUser?.id]` בלבד, ולכן
אינו רץ מחדש במהלך מסע הבדיקה. חשוב מזה: הוא **מחליף state בלבד**
(`// REPLACE — not merge`, שורה 1517). hydration אינה יכולה להחזיר שורה למסד.

> hydration היא **איך המשתמש רואה** את הרפאים חוזר במפגש הבא — **לא למה** הוא
> שרד ב-DB. תיקון ב-hydration היה מטפל בתסמין ומשאיר את השורש.

### השורש — שני פגמים שמתחברים

**(א) ה-INSERT הוא fire-and-forget.**
`SwingEdge_App.jsx:2416-2418` יורה
`supabase.from("trades").insert(...).then(({error}) => ...)`
**בלי `await`, ובלי לשמור את ה-promise בשום מקום.** `handleSubmit` חוזר מיד,
מנווט ל-`journal` (שורה 2422), והשורה מוצגת בטבלה **מה-state המקומי בלבד**.

`handleDeleteTrade` (`:2478-2481`) יורה `DELETE` מסונן על `id`. אם ה-INSERT
טרם נחת, ה-DELETE מתאים **אפס שורות** — ואז ה-INSERT התלוי נוחת **אחריו**.
התוצאה: השורה קיימת ב-DB, נעלמה מה-state.

**(ב) DELETE שמתאים אפס שורות מחזיר `error: null`.**
זו התנהגות PostgREST, לא באג. לכן `if (error)` ב-`:2482` **אינו יכול** לתפוס
את המקרה, ו-`toast.success` ב-`:2485` הוא **ללא תנאי**.

> **שום בדיקת שגיאה, טובה ככל שתהיה, לא תתפוס את זה. רק בדיקת מונה שורות.**
> זו הסיבה שהכשל שקט, וזו הסיבה ש"להוסיף `if (error)` טוב יותר" אינו תיקון.

**התקדים כבר בריפו:** `admin_delete_trade`
(`20260719120000_admin_rpcs.sql:395-405`) עושה
`get diagnostics _n = row_count; return _n`.
**מסלול האדמין מאמת מונה שורות. מסלול המשתמש לא.**

## §2 — התיקון

### מודול טהור חדש: `src/lib/tradeDelete.js`

תקדים מפורש: `src/lib/replyGate.js` הוצא למודול טהור **בדיוק** כדי שיהיה
בר-אסרציה בשרשרת החוסמת (`scripts/notify-handle-test.mjs:24-31`).
`SwingEdge_App.jsx` בן 7,308 שורות ואינו ניתן לייבוא ב-node (recharts, lucide).

```
deleteTradeRow(client, { id, userId }) → { ok, reason, message }
```

- מבצע `.delete().eq("id", id).eq("user_id", userId).select("id")`
- `ok: true` **רק** כאשר חזרה **בדיוק שורה אחת**
- `error` שאינו null → `{ ok:false, reason:"error", message: error.message }`
- אפס שורות → `{ ok:false, reason:"not-found" }`

### `handleDeleteTrade`

1. **ממתין ל-INSERT התלוי** של אותו `id` — מפת `pendingWrites` ב-`useRef`,
   מאוכלסת ב-`handleSubmit` (`:2416`) ומתנקה ב-settle. **זה מה שסוגר את המרוץ.**
2. שומר את העסקה **ואת האינדקס שלה** לפני ההסרה.
3. הסרה אופטימית (מותרת, כפי שנקבע בפרומפט).
4. `!ok` → **מחזיר את השורה לאינדקס המקורי** + `toast.error` עם ההודעה כלשונה.

⛔ אפס `catch` שותק. השגיאה מוצגת למשתמש כלשונה.

**למה אינדקס ולא append:** `prev.filter()` מאבד מיקום. החזרה בסוף המערך הייתה
מקפיצה את השורה למקום אחר בטבלה — rollback שנראה כמו באג שני.

### rollback מול hydration

`setTrades` הוא REPLACE-not-merge, ו-hydration רצה רק על שינוי `authUser.id`.
ה-rollback מחזיר שורה ש**באמת קיימת ב-DB** — ולכן ה-hydration הבאה תמשוך בדיוק
את אותה שורה. **ה-rollback וה-DB מסכימים; אין דריסה.**
