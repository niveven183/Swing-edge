## 4. השינויים בקוד

### 4.1 `api/notify.js` — הרחבת `TEMPLATES`

שבעה מפתחות חדשים, עם דגל שמבדיל אותם מהישנים:

```js
export const TEMPLATES = {
  fix_mobile_upload: { file: "...", subject: "...", },   // ⛔ ללא שינוי
  files_received:    { file: "...", subject: "...", },   // ⛔ ללא שינוי
  reply_bug_fixed:   { file: "emails/reply_bug_fixed.html", subject: "…", body: true },
  … 6 נוספים, כולם body: true
};
```

`body: true` הוא **מקור-האמת-האחד** לשאלה "האם התבנית דורשת ליבה". הפאנל
לא מחזיק רשימה משלו — הוא מקבל את הדגל מ-`GET` (§4.4).

⚠️ `GET` ממשיך להחזיר `key` + `subject` בלבד **פלוס** `body` (בוליאני).
⛔ לא נתיב קובץ, ⛔ לא HTML — אסרציה 3 הקיימת אוכפת את זה ותמשיך לרוץ.

### 4.2 `{{BODY}}` — הזרקת הליבה

**תקרת אורך: 2000 תווים.** הנימוק:
- **למה לא פחות:** מענה באג מפורט אמיתי (07.08, `fix_mobile_upload`) הוא
  ~900 תווי ליבה. תקרה של 1000 הייתה חוסמת אותו על הסף.
- **למה לא יותר:** אחרי `escapeHtml` תו יכול לתפוח פי 6 (`&`→`&amp;`),
  כלומר גבול עליון תיאורטי של ~12KB. Gmail גוזם הודעה סביב **102KB**;
  השלד הוא ~5KB. 2000 משאיר מרווח של פי 8 ואינו יכול להתקרב לגזימה.
- **מינימום:** לא-ריק אחרי `trim()`. ⛔ ליבה ריקה בתבנית `body: true` → 400.

| מצב | תשובה |
|---|---|
| תבנית `body: true` בלי `body_text` (או ריק אחרי trim) | `400 body_text_required` |
| `body_text` > 2000 תווים | `400 body_text_too_long` |
| תבנית ישנה **עם** `body_text` | `400 body_text_not_supported` — ⚠️ ראה למטה |
| תבנית ישנה **בלי** `body_text` | ✅ 200, זהה לחלוטין להיום |

⚠️ **למה 400 ולא התעלמות שקטה** בשורה השלישית: אדמין שהקליד ליבה ובחר
תבנית קפואה יקבל מייל שאינו מכיל את מה שכתב, בלי שום סימן. זה בדיוק
"כשל שקט" של §2. ⛔ **זה אינו שובר את שתי הישנות** — הפאנל אינו מציג
תיבת ליבה עבורן, ולכן הן ממשיכות להישלח בדיוק כמו היום.

**הרינדור:**

```js
const escapeHtml = (s) => String(s)
  .replace(/&/g, "&amp;").replace(/</g, "&lt;").replace(/>/g, "&gt;")
  .replace(/"/g, "&quot;").replace(/'/g, "&#39;");

// escape → split לפסקאות (\n\n+) → \n בודד ל-<br>
function renderBody(text) {
  return String(text).replace(/\r\n/g, "\n").trim()
    .split(/\n\s*\n+/)
    .map((p) => `<div style="font-size:15px;color:#3d4a44;line-height:1.75;margin:0 0 16px;">${
      escapeHtml(p).replace(/\n/g, "<br>")}</div>`)
    .join("");
}
```

⚠️ **מלכודת שנחסמת במפורש:** ההזרקה חייבת להיות
`html.replace("{{BODY}}", () => rendered)` — **עם פונקציה**. מחרוזת החלפה
רגילה מפרשת `$&`, `$'`, `` $` `` — ליבה שמכילה `$&` הייתה משכפלת את
`{{BODY}}` לתוך המייל. יש על זה אסרציה (§5, מס' 20).

⚠️ **`escapeHtml` רץ על הפסקה, אחרי הפיצול.** הפיצול לפני ההברחה בטוח:
`\n` אינו מיוצר על-ידי ההברחה ואינו נהרס על-ידה.

⛔ **אפס HTML מהקלט.** אין allowlist תגיות, אין markdown, אין קישורים.
טקסט + שבירת שורה בלבד. הרחבה כזו היא החלטה נפרדת, לא "בדרך".

### 4.3 `reply:<feedback_id>:<n>` — פתיחת המנעול

**הבעיה:** `campaign = "reply:<id>"` ייחודי לנצח → לפידבק אפשר לענות
פעם אחת בלבד. זה סותר ישירות את המודל החדש: `reply_bug_ack` היום
("בטיפול") ו-`reply_bug_fixed` בעוד שבוע ("תוקן") הם **שני מיילים
לאותו פידבק**, וזה התסריט המרכזי של §3.

**המנגנון:**

1. קריאה אחת לליגר: `campaign=like.reply:<id>*` · `select=campaign,status`
   · `limit=200`. ⚠️ נשמר **fail-closed** כמו היום: ליגר שאי-אפשר לקרוא
   → `503 ledger_unavailable`, לא "מותר לשלוח".
2. **`n = max(n קיים) + 1`** — מחושב **בשרת בלבד**.
   ⛔ הלקוח אינו שולח `n` ואינו יכול להשפיע עליו.
3. **back-compat:** שורה בפורמט הישן (`reply:<id>` בלי `:n`) **נספרת
   כ-`n=1`**. שתי השורות הקיימות — `reply:eebd6bb1…` (07.08 12:06) ו-
   `reply:f95b837e…` (07.08 19:09) — ולכן המענה הבא להן יהיה `n=2`.
   **אסרציה ייעודית (§5, מס' 16).**
4. ⚠️ שורה שנרשמה `status='failed'` **כן** צורכת `n`. `n` הוא זהות, לא
   מונה הצלחות; שריפת מספר עדיפה על שני מיילים שונים באותו מפתח.

**החלטה שדורשת את הכרעת ניב — מבנה המפתח**

`STATE` מציין `reply:<id>:<n>`. ⚠️ **`:n` לבדו מסיר את ההגנה מפני
שליחה כפולה ואינו מחזיר דבר במקומה** — האדמין לוחץ "שלח" פעמיים,
המערכת מחשבת `n=1` ואז `n=2`, ושולחת את **אותו מייל בדיוק** פעמיים.
היום זה בלתי אפשרי, ואחרי השינוי — חופשי.

| | א׳ — `reply:<id>:<n>` (כלשון `STATE`) | ב׳ — `reply:<id>:<n>:<h8>` **← מומלץ** |
|---|---|---|
| תשובה עוקבת (תוכן שונה) | ✅ | ✅ |
| כפילות מדויקת (double-click / שליחה חוזרת בהיסח) | ⛔ **עוברת** | ✅ נחסמת `409 duplicate_reply` |
| מנגנון | — | `h8` = 8 תווים ראשונים של SHA-256 על `template + "\n" + body_text.trim()`, `node:crypto` |
| מיגרציה | לא | לא — עוד קטע במחרוזת (~55 תווים סה"כ) |
| מחיר | — | שליחה מכוונת של אותו תוכן פעמיים דורשת שינוי תו אחד |

**המלצה: ב׳.** המחיר הוא תסריט שכמעט תמיד הוא טעות; התמורה היא שההגנה
היחידה שיש היום לא נעלמת. ⚠️ בשתי החלופות שתי השורות ההיסטוריות
**נטולות טביעה**, ולכן אינן חוסמות שום מענה חדש — בכוונה.

⛔ **אם ניב בוחר א׳ — אומרים זאת מפורשות ב-`DECISIONS`**, כולל שההגנה
מפני כפילות עוברת כולה לצד הלקוח (`replyGate` + `busy`), שהוא צד
שאי-אפשר לסמוך עליו.

**`src/lib/replyLedger.js` — מודול טהור חדש**

הפאנל היום עושה `String(r.campaign).slice("reply:".length)` — עם המפתח
החדש זה מחזיר `<id>:2` ו**שתי השורות ההיסטוריות נעלמות מהמסך בשקט**.
הפירוק עובר למודול טהור (אותה סיבה בדיוק כמו `replyGate.js`:
`AdminPanel.jsx` אינו נטען ב-node, ולכן אי-אפשר לאסרט עליו ב-`verify`):

```js
parseCampaign("reply:<id>")           → { id, n: 1, hash: "" }
parseCampaign("reply:<id>:3")         → { id, n: 3, hash: "" }
parseCampaign("reply:<id>:3:a1b2c3d4")→ { id, n: 3, hash: "a1b2c3d4" }
parseCampaign("why_stopped")          → null
summarize(rows) → { [feedbackId]: { count, lastSentAt, lastStatus } }
```

### 4.4 הידית בפאנל (`AdminPanel.jsx`)

1. **בורר תבנית** — 9 אפשרויות (7 חדשות + 2 ישנות), כולן מ-`GET`.
   ⛔ אפס שם תבנית ב-`AdminPanel.jsx` — אסרציה 6 הקיימת אוכפת.
2. **תיבת ליבה** — `<textarea>` שמופיעה **רק** כאשר `t.body === true`
   עבור התבנית הנבחרת. מונה תווים `n/2000`, אדום מעל התקרה.
3. 🔴 **היבש מציג את הגוף המלא המורנדר.** זו הנקודה שנרשמה ב-07.08:
   עם תוכן קפוא `html_bytes` היה אימות מספיק; **עם תוכן חופשי, מספר
   bytes אינו מאמת כלום** — הוא זהה בין ליבה נכונה לליבה שהודבקה לשדה
   הלא נכון. היבש יציג:
   - נושא · נמען ממוסך · `n` הצפוי (״זו תהיה תשובה מס' 2״) — כמו היום
   - **`<iframe srcDoc={html} sandbox="" />`** — הגוף כפי שהנמען יראה
     אותו, בגובה ~420px.
     ⚠️ `sandbox=""` **ריק לחלוטין** — בלי `allow-scripts` ובלי
     `allow-same-origin`. תצוגה מקדימה אינה יכולה להריץ דבר ואינה
     יכולה לגעת במסמך האב. זה גם מה שהופך את התצוגה עצמה לבטוחה
     גם אם `escapeHtml` ייכשל יום אחד.
   - `api/notify.js` יחזיר `html` בתשובת ה**יבש בלבד**.
     ⛔ לא ב-`GET`, ⛔ לא בתשובת שליחה.
4. **`replyGate`** — `reduce` מקבל אירוע חדש `{type:"body", text}` שמאפס
   את `verifiedFor`, בדיוק כמו החלפת תבנית. ⚠️ **עריכת הליבה אחרי יבש
   מוצלח היא בדיוק הדרך לשלוח משהו שלא נצפה** — הוא הסיכון שהגל הזה
   מכניס, והוא נסגר באותו מנגנון שכבר קיים.
5. **ליד פידבק שנענה:** `✉ נשלחו 2 תשובות · אחרונה 07.08 19:09` —
   מ-`summarize()`, כלומר מהליגר. ⛔ עדיין `campaign,sent_at,status`
   בלבד — **עמודת המייל אינה נבחרת**, כמו היום.
