### 2.1 ה-API אחרי ההרחבה

הליבה היא סיווג טהור אחד, ושאר הפונקציות הן מקרים פרטיים שלו. **אפס לוגיקה כפולה:**

```
classifyRows({ data, error }, expected)   ← הליבה. טהורה, נבדקת לבדה
  → { ok, reason: "error"|"none"|"partial"|"too-many"|"written", rows, message }

insertTradeRow (expect 1)     updateTradeRow (expect 1)     deleteTradeRow (expect 1) ← קיימת, ללא שינוי התנהגות
insertTradeRows (expect n)    deleteTradeRows (expect n)    ← bulk: מחזירות גם את ה-ids שחזרו
restoreAt · createPendingWrites · deleteTradeVerified       ← ללא שינוי כלל
```

**⛔ מה שלא משתנה:** הסמנטיקה של `deleteTradeRow` — `ok` על בדיוק 1, `not-found` על 0,
`too-many` על >1, שגיאה כלשונה. 7/7 האסרציות הקיימות חייבות להישאר ירוקות ביט-בביט.
זהו קו הבסיס הקפוא של הגל הקודם, וזזה בו = STOP.

**למה ה-bulk מחזירות ids ולא רק מונה:** בלי לדעת **אילו** שורות לא נמחקו אי-אפשר
להחזיר את הנכונות ל-state — rollback על כולן היה מחזיר גם את ה-3 שכן נמחקו.

### 3.1 §1 — הפרטים שקובעים

```
const p = insertTradeRow(supabase, { trade, userId });
pendingWrites.track(newTrade.id, p);        // ⚠️ track לפני ה-await, אחרת המרוץ חוזר
const res = await p;
if (!res.ok) { setTrades(prev => prev.filter(t => t.id !== newTrade.id)); toast.error(...); }
```

- ⚠️ **`track` נרשם לפני ההמתנה** — אחרת מחיקה שיוצאת באמצע לא תמתין, וזה המרוץ המקורי.
- ✅ **settle מובטח:** `insertTradeRow` לעולם לא זורקת (מחזירה ערך), ולכן ההבטחה תמיד
  נפתרת ו-`pendingWrites` משחרר בכל מסלול, כולל כשל. אין תלייה.
- ⛔ **ה-optimistic לא משתנה:** `setTrades` ב-`:2422` נשאר ראשון, הטופס נסגר, `setTab`
  נשאר. ה-UI **אינו** נחסם בזמן ההמתנה. רק הסוף אומר אמת.
- ⚠️ **קצה מוכר:** אם המשתמש מוחק עסקה בזמן שה-INSERT שלה באוויר וה-INSERT נכשל —
  המחיקה תמתין, תמצא 0 שורות, ותדווח `not-found`. שני toast על אותה עסקה. **מקובל:**
  שתי ההודעות נכונות, ואף אחת אינה שקטה.
