## 1. השורש המדוד — state שרד, ⛔ race

`capital`, `userProfile`, `accountCurrency`, `capitalCurrency`, `riskPct`, `lang`,
`watchlistItems`, `priceAlerts`, `playbookSetups` — כולם `useState` ברמת הקומפוננטה,
מאותחלים **פעם אחת בלבד** ב-mount הראשון, מ-localStorage **לא-משויך-למשתמש**:

```
:1349  useState(() => localStorage.getItem("swingEdgeCapital") ...)
:1190  useState(() => localStorage.getItem("swingEdgeOnboarding") ...)   // userProfile
:1612  useState(() => localStorage.getItem("swingEdgePriceAlerts") ...)
:1626  useState(() => localStorage.getItem("swingEdgePlaybook") ...)
:1684  useState(() => localStorage.getItem("swingEdgeWatchlist") ...)
```

`handleLogout` (`:1272-1278`) מנקה **רק** `session` ו-`showProfileDropdown`.
⛔ אף אחד מה-state הללו לא מתאפס, ו⛔ אף אחד לא תלוי ב-`authUser?.id` בצד הקריאה.
`hydratedRef` (D-lite, `B-361`) גודר **רק** את אפקט הכתיבה (`:1870`) — ⛔ אינו נוגע
ברינדור ו⛔ אינו מאפס state.

**הרצף המדויק:**

1. A מחובר, `capital=A`.
2. Logout → `authUser` → `null`. אפקט ההידרציה (`:1745`, תלוי `[authUser?.id]`) יורה:
   `hydratedRef.current = false` (`:1752`), ואז `!authUser?.id` → `return` מיידי.
   `capital` **לא זז**.
3. Login ל-B, אותו טאב. React מרנדר עם `authUser.id = B` ו-`capital` **עדיין של A** —
   **זה בדיוק הפריים שניב ראה.**
4. אפקט ההידרציה יורה שוב, ומתחיל `await migrateFromLocalStorage(B)` →
   `await loadSettings(B)` — שני round-trips. לאורך כל החלון `capital` נשאר של A.
5. `loadSettings` חוזר → `setCapital(B)` (`:1793`) ואז, **באותו בלוק סינכרוני**,
   `hydratedRef.current = true` (`:1857`) → repaint. זה מה שניב ראה כ«עבר».

**המנגנון: ⛔ race.** ההשמה `hydratedRef.current = false` קורית סינכרונית, הרבה לפני
שבקשת רשת של B יוצאת. זו ההשערה השנייה של ניב: **state ישן פשוט שורד עד ה-`setXxx`
הבא**, כי ⛔ אין קוד שמאפס אותו בין A ל-B.

## 3. 🔴 זו דליפה לשרת — P1, ⛔ display-only

`watchlistItems`/`priceAlerts`/`playbookSetups` מוגנים ב-`had()` (`:1759-1769`),
שנמדד **לפני** ה-await — כלומר על ה-localStorage של **A**, כי שום דבר לא ניקה אותו
ב-logout. לכן אם ל-A היה watchlist לא-ריק, `hadWatchlist === true` ⇒ שורה `:1822`
**מדולגת** ⇒ `watchlistItems` נשאר **של A**, גם אחרי שההידרציה של B הסתיימה.

**ואפקט ההתמדה כולל אותם ב-patch — נמדד:**

```
:1875  const patch = {
:1876    capital, riskPct, lang, accountCurrency, capitalCurrency,
:1877    watchlist: watchlistItems.map(({ticker,setup,chartSym}) => ({ticker,setup,chartSym})),
:1878    priceAlerts,

:1892  saveSettings(authUser.id, patch);     // authUser.id === B
```

⇒ **B משנה הון ⇒ `capital` משתנה ⇒ האפקט יורה (`hydratedRef===true`, כי B כבר
עבר הידרציה) ⇒ ה-patch נושא את ה-watchlist/alerts/playbook של A ⇒ נכתב לשורה של B.**

**הכרעת חומרה: P1 — דליפת נתונים בין-חשבונות לשרת.** הגרסה הראשונה של המסמך בדקה
רק את חלון ה-flash (שבו אכן אף תלות לא זזה ולכן האפקט ⛔ יורה) ו**עצרה שם** — היא
⛔ בדקה את המצב **אחרי** שההידרציה הסתיימה, שבו `hydratedRef` **פתוח** וה-state
**עדיין מעורב**. זה `‹R-2›` בצורתו הטהורה: הכרזה על היעדר על בסיס חלון שלא יכול
להכיל את הנמדד.

**מה כן נשאר נכון מהגרסה הראשונה:** `capital` עצמו ⛔ יכול לדלוף — ההידרציה דורסת
אותו ללא תנאי `had()` (`:1792`), ולכן בזמן שהאפקט יורה הוא כבר של B. הדליפה היא
בשלוש הקולקציות המוגנות-`had()` בלבד, ובנוסף `onboarding` (`:1886-1890`) שנקרא
מ-`localStorage` הגלובלי בזמן בניית ה-patch — **⚠️ אותו מסלול בדיוק, ⛔ נמדד לעומק
כאן; הוא חייב להיכלל באודיט הביצוע.**

**חשיפה בפרודקשן — `0/49` היום, וזה חלון ⛔ מצב:**
`49/49` שורות `user_settings` נושאות אחת משתי קבוצות watchlist **ברירת-מחדל** בלבד
(`47/49` את ברירת המחדל הישנה בת `10` טיקרים · `2/49` את הנוכחית בת `14`).
`playbook` לא-ריק: `0/49`. `priceAlerts` לא-ריק: `0/49`.
⇒ **היום ⛔ אף משתמש ⛔ מותאם-אישית, ולכן ⛔ ניתן להצביע על דליפה שקרתה בפועל.**
⛔ **ואסור לקרוא את זה כ«הבאג לא קיים»** — המשתמש הראשון שיתאים watchlist ויחליף
חשבון באותו דפדפן חשוף; אותו לקח בדיוק של `M-018`.

## 5. כיוון התיקון — מדידת שתי החלופות

### (א) remount — `key={authUser?.id}`

**היתכנות נמדדה:** `<SwingEdge />` ממוקם ב-`main.jsx:169` בתוך `<Route path="/app">`,
ו-**מצב ה-auth חי בתוך `SwingEdge` עצמו** (`:1252-1270`, `setSession`).
⇒ צריך wrapper דק **מעל** הקומפוננטה שמחזיק את ה-session.

⚠️ **הרפקטור המלא (הרמת ה-auth החוצה והעברתו כ-prop) הוא רחב: `64` אזכורי
`authUser` + `24` אזכורי `session` בקובץ.** לכן הגרסה המינימלית:
wrapper ב-`main.jsx` שנרשם ל-`onAuthStateChange` **רק כדי לקרוא את ה-uid**,
ומרנדר `<SwingEdge key={uid ?? "anon"} />`. `SwingEdge` נשאר **ללא שינוי** ב-88
אתרי האזכור. המחיר: שני מאזינים לאותו auth client — זול, ונכון מול רפקטור של 88 אתרים.

⚠️ **שתי סכנות שחייבות טיפול באותו קומיט:**
1. **remount לבדו ⛔ מתקן — הוא מריץ מחדש את אותם `useState` initializers מול אותו
   localStorage גלובלי** ⇒ B יאותחל מה-mirror של A. ⇒ **חובה ניקוי ב-logout.**
2. **remount בטעינה הראשונה** (`undefined → uid`) יזרוק את העץ פעם אחת.
   ⇒ ה-wrapper ⛔ מרנדר עד ש-`getSession()` נפתר (`authReady`), כך שה-key יציב
   מה-mount הראשון.

🆕 **והניקוי ⛔ יהיה רשימת-מפתחות-למחיקה — זו בדיוק הרשימה שתירקב.**
**מהפכים אותה: allowlist של מפתחות ברמת-מכשיר שנשמרים, וכל שאר `swingEdge*` נמחק.**
⇒ מפתח **חדש** שמישהו יוסיף מחר נמחק **כברירת מחדל** (בטוח), ורק מפתח שהוא
מוצהרת-מכשיר נכנס לרשימה. זו התכונה המבנית שניב ביקש: **כשל ברירת-המחדל בטוח.**
לפי §2: `8` נשמרים · `17` נמחקים.
