## 0. השורש, בניסוח המתוקן של ניב

הערת הקוד ב-`api/quote.js:367-371` טוענת "מרווח של פי-14" — אבל המונה שם הוא
**בקשות ל-`/api/quote`** (4.2/דקה, לפי משתמש), בעוד התקרה האמיתית (60/דקה) היא
ביחידת **קריאות-Finnhub בפועל**. בקשה אחת עם עד 60 סימבולים מייצרת עד 54 קריאות
Finnhub סימולטניות (חלק מהסימבולים הם קריפטו → CoinGecko, לא נספרים). ⇒ **בקשה
בודדת אחת, קרה, צורכת ~54/60 ≈ 90% מכל תקציב הדקה של Finnhub** — לא פי-14 מרווח,
אלא כמעט אפס. זהו R-1 בצורתו הטהורה: מסקנה נכונה מבחינה חשבונית, שגויה ביחידה.

**מה שבורר, לא הנפח:** TwelveData צורכת 440/800 קרדיטים ב-13.5 שעות היום — נפח
סביר. הבעיה היא שה-54 קריאות יוצאות **בו-זמנית**, לא לאורך זמן. תיקון-הנפח (למשל
כיווץ `FH_TTL`) לא יעזור; תיקון-הצורה (concurrency cap) הוא הכיוון שניב הורה.

## 1. 🔴 Concurrency cap על הפאנ-אאוט (`api/quote.js:458-460`)

### 1.1 מצב היום

```js
// Stocks fan out in parallel; allSettled keeps one bad symbol from failing all.
const settled = await Promise.allSettled(
  stockSyms.map((sym) => finnhubResult(sym, KEY))
);
```

עד 54 קריאות `finnhubResult` יוצאות באותה מילישנייה.

### 1.2 מדד-העוגן (⛔ לא מומצא)

Finnhub, טיר חינמי (`AUDIT-B176.md` D1, מאומת ב-WebSearch מול `finnhubio/Finnhub-API`
issue #122 + apicostcalc.com): **60 קריאות/דקה + תקרת-פנים 30 קריאות/שנייה**.

concurrency cap **לא מקטין** את מספר הקריאות (זה קבוע לפי מספר הסימבולים) — הוא
**פורס אותן על פני זמן** כך שבקשה בודדת לא תופסת את כל חלון ה-30/שנייה לבדה,
ומשאירה מרווח לתעבורה מקבילה (טאבים אחרים, משתמשים אחרים) **בתוך אותה שנייה**.

**נגזרת הערך:** `30/שנייה ÷ 3` (מקדם-ביטחון לתעבורה מקבילה שאינה נראית לבקשה
הנוכחית) **= 10 קריאות בו-זמנית לכל היותר, לכל בקשת `/api/quote` בודדת.**

### 1.3 עלות בזמן-המתנה למשתמש — מדוד, לא משוער

מדידת latency אמיתית של קריאת-Finnhub בודדת, דרך `/api/health` (`checks.finnhub`,
מדידה חיה ב-25.08, שתי דגימות במרווח 21 שניות כדי לעקוף cache 20-שניות פנימי):
**52ms, 55ms.**

עם cap=10 ו-54 סימבולי-מניה: `ceil(54/10) = 6` באצ'ים סדרתיים, `Promise.allSettled`
בתוך כל באץ'. עלות מתווספת גסה: `6 × ~55ms ≈ 330ms`. **זה לא 60 שניות** (הסף
שניב ציין כפסילה) — זה תוספת תת-שנייה למשתמש שממילא ממתין ל-fetch רשתי.

### 1.4 מגבלה כנה — ⛔ לא נפתרת בפתרון הזה

Vercel serverless: כל בקשה נכנסת עלולה לרוץ ב-instance נפרד. cap-פר-בקשה מיישר
את ה-burst **הפנימי של אותה בקשה**, אבל **לא** יוצר תקציב משותף בין-בקשות/בין-
instances. שני משתמשים ששולחים בקשה **באותה שנייה בדיוק**, כל אחד עם cap=10
פנימי משלו, עדיין יכולים ביחד לחצות את תקרת ה-30/שנייה. **זה משפר משמעותית את
המקרה הנפוץ (בקשה בודדת/thundering-herd מטאבים של אותו משתמש — בדיוק מה שנצפה
בלוג ב-D2), ⛔ לא פותר קואורדינציה בין-משתמשים** (זה ידרוש store חיצוני משותף —
מחוץ להיקף).

### 1.5 מימוש מוצע (טרם נכתב)

פונקציית `pLimit`-סגנון מקומית (batching פשוט, בלי תלות חדשה): לחלק את
`stockSyms` למקטעים בגודל 10, `await Promise.allSettled` על כל מקטע ברצף,
לצבור תוצאות. `cap = 10` כקבוע בראש הקובץ עם הערה שמצטטת את המדד (30/שנייה ÷ 3)
כדי שהמספר לא ייראה שרירותי לקורא הבא.

## 2. 🔴 תיקון ההערה המטעה (`api/quote.js:367-371`) — **באותו שינוי**

תקדים: `src/lib/tradingStats.js:64`, תוקן ב-`B-143` — הערה שגויה-בנימוק שהושארה
כמלכודת לחוקר הבא.

**הישן** (יחידה שגויה — סופר בקשות, לא קריאות-Finnhub):
> "60/min per IP is deliberately ~14x the legitimate peak..."

**החדש (מוצע):** להבהיר במפורש ששני מספרים שונים חיים כאן, ולא לבלבל ביניהם:
- `rateLimit()` כאן מגן מפני **ניצול-לרעה של הפרוקסי לפי IP** (בקשות ל-`/api/quote`,
  לא קריאות-Finnhub). זה מספר שפיר ורחוק מהתקרה.
- **תקרת Finnhub האמיתית (60/דקה + 30/שנייה) נמדדת ביחידת קריאות-Finnhub-בפועל**,
  והיא נצרכת ב-`Promise.allSettled` למטה (עד 54 קריאות מבקשה בודדת) — ⛔ לא כאן.
  בקשה קרה בודדת יכולה לצרוך לבדה ~90% מהתקציב הזה. ראה concurrency cap (§1).

## 3. ⚠️ תג ה-LIVE המטעה — שני אתרים, תיקון מינימלי end-to-end

### 3.1 המנגנון (חמור יותר ממה שתועד באבחון המקורי)

`finnhubResult` (`api/quote.js:139-167`), בכשל HTTP (שורה 147-149):

```js
if (!r.ok) {
  console.error(`Finnhub quote failed: HTTP ${r.status}`);
  return cached ? cached.result : null; // stale fallback — 15s-old price beats null
}
```

התוצאה המוחזרת **זהה במבנה** לתגובה טרייה — **אין סמן** שמבדיל, וה-staleness
**לא חסום בזמן**: רק fetch מוצלח (שורה 165) מרענן `cached.ts`. בכשל ממושך, מחיר
בן דקות יכול לחזור נראה כמו "עכשיו".

### 3.2 תיקון מוצע — שרשור שדה `stale` תוסף (additive-only, §13 CLAUDE.md)

1. **`api/quote.js`** — ב-fallback (שורה 149), להוסיף שדה עליון `stale: true`
   לאובייקט המוחזר (שדה חדש, ⛔ לא משנה/מסיר שדה קיים):
   ```js
   return cached ? { ...cached.result, stale: true } : null;
   ```
2. **`src/priceService.js`** — ב-`parseChartResult`, לשרשר `isStale: !!raw?.stale`
   לתוך אובייקט ה-quote המוחזר ללקוח (שדה חדש בצורת ה-return המתועדת).
3. **`SwingEdge_App.jsx`** — שני האתרים, לגייט את התג על `isStale` **בנוסף** ל-
   `marketOpen`:
   - טופס הוספת-עסקה (~שורה 7605-7614): `marketOpen && !q?.isStale`
   - Trade Analyzer (~שורה 5334-5343): `marketOpen && !analyzerQuote?.isStale`
     (**אתר שני, לא תועד באבחון המקורי** — התגלה בקריאה חוזרת של הקוד;
     אותו דפוס-באג בדיוק, אותו תיקון).

**⛔ לא רידיזיין** — אין שינוי ל-cache TTL, ל-`FH_TTL`, או ללוגיקת ה-badge
מעבר לתנאי הנוסף היחיד.

### 3.3 מה **לא** בהיקף הסעיף הזה — הועלה לניב, לא הוכרע

`openPnL`/`getLivePrice` (הפולר הגלובלי, `SwingEdge_App.jsx:2439-2480`) צורכים
ישירות `livePrices[ticker]` **בלי** שום סמן staleness — טיקר שנתקע אחרי 429
מזין P&L חי בלי סימון. זה **לא** אחד משני האתרים שניב תיחם בסעיף 3 (טופס
הוספת-עסקה + Analyzer), ונרשם בנפרד כ-`B-182` (§4) עם סטטוס חסום-על-ניב.
**שאלה פתוחה לניב:** האם לכלול את `livePrices`/`openPnL` בתיקון הזה (התשתית
ב-§3.2 יכולה לכסות גם אותו, כי `getLivePrice` יכול לבדוק `isStale` על אותו
אובייקט) — או להשאיר את זה כגל נפרד. **לא הכרעתי בעצמי** כדי לא להרחיב היקף
שהוגדר במפורש בסעיף 3 של ההנחיה.

## 6. תנאי-הצלחה ומדידה — **אחרי deploy בלבד**

### 6.1 למה לא להשתמש בבסיס `2622`/`2839` כמו שהוא

`AUDIT-B176.md` D6 גילה ש-`first=2026-07-09` **קבוע** בשתי המדידות (24.08, 25.08)
**למרות** בקשת `since=7d` — כלומר שדה ה-aggregate של `get_runtime_errors` כנראה
**לא כפוף בפועל לחלון המבוקש**. משמעות: `count=2622`/`2839` הם ככל הנראה
מצטברים-מאז-ומעולם, ⛔ לא "שבוע אחרון", ו**אין מכנה-זמן אמין לנרמל לפיו ליום**.
השוואה ישירה של `2622` ל"429-ים ביום אחד אחרי הפריסה" היא בדיוק הטעות שתועדה
ב-`AUDIT-B171c` (מצטבר מול יומי) — ⛔ לא תיעשה כאן.

### 6.2 המדד הנכון: `get_runtime_logs`, לא `get_runtime_errors`

`get_runtime_logs` תומך ב-`group_by`/סינון על `statusCode`+`route`+טווח-זמן
אמיתי (⛔ לא cluster aggregate גלובלי). **נוהל:**

1. לבדוק את חותמת-הזמן של ה-deploy בפועל (Vercel) — **לפני** כל מדידה.
2. לחכות חלון-מדוד **24 שעות UTC אחרי** אותה חותמת (⛔ לא לפני).
3. לשלוף מ-`get_runtime_logs`: `statusCode=429`, `route=/api/quote`, טווח-זמן
   מפורש = אותן 24 השעות. זה מספר יומי-אמיתי, בר-השוואה לעצמו בעתיד — ⛔ לא
   ל-`2622`/`2839`.
4. לדווח את המספר **עם** החלון המדויק שנמדד (תאריך+שעת-התחלה/סיום UTC).

### 6.3 §10 מלא + DONE

לפני push: `npm run verify` (23 חוליות + build), פלט מלא מודבק. אחרי מדידת 6.2:
שורת `DONE` בפורמט 4.1 (מזהה · תאריך · hash · איך-אומת) **בקומיט הבא** (לא
יכול לשאת את ה-hash של עצמו).
